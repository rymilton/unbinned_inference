# unbinned_inference

Neural simulation-based inference (NSBI) for determining the Pythia generation parameters that best
reproduce **unbinned unfolded H1 data** (HERA *ep* deep inelastic scattering).

## Overview

Conventional generator tuning compares simulation to data through a handful of binned summary
observables, discarding most of the information in each event. This analysis instead makes the
comparison unbinned and in the full high-dimensional phase space.

A neural network learns a per-event likelihood ratio between Pythia generated at a given set of
parameters and a fixed reference sample. The ratio is obtained by classification: a classifier
trained to separate the two samples has an output `f` from which the density ratio follows as
`f / (1 - f)`, which reweights one sample into the other. That learned ratio acts as a **surrogate
likelihood**, which can then be evaluated against unfolded H1 data to infer the generation
parameters and their uncertainties.

Several Pythia generation parameters are inferred, not just one. The strong coupling
α<sub>s</sub> is the first implemented, and the dataset manifest and configuration plumbing are
written for an arbitrary parameter list so additional parameters can be added without code changes.

The classifier is **parameterized**: the generation parameters are supplied to the network as
additional event-level input features, so a single model covers the whole parameter space
continuously, rather than requiring a separately trained model at every point.

The network is a PET-style (Point-Edge Transformer) point-cloud model: local *k*-NN feature
extraction followed by multi-head-attention transformer blocks, with a class-token head conditioned
on event-level features through FiLM-style scale/shift modulation.

**Current status.** The pipeline is being developed and validated Pythia-against-Pythia, where the
"data" side is simulation at a known parameter point — a closure test with a known right answer.
Unfolded H1 data is the eventual target of the inference.

## Repository layout

```
pythia_generation/     Pythia8 event generation (C++) and FastJet jet clustering
scripts/               ML pipeline: data prep, dataloader, model, training, analysis
configs/               Training hyperparameters and the dataset manifest
environment.yml        Conda environment definition
install_horovod.sh     Horovod build script (must run separately -- see Setup)
CLAUDE.md              Detailed internals and gotchas for contributors
```

Data and model artifacts are gitignored and regenerated by the pipeline — `pythia_files/` (raw ROOT),
`pythia_h5/` (HDF5), `clustered_pythia_files/`, `weights/` (checkpoints), and `plots/`.

## Setup

```bash
conda env create -f environment.yml
conda activate unbinned_inference
./install_horovod.sh
```

Horovod is installed separately because its build reads environment variables
(`HOROVOD_GPU_OPERATIONS`, `HOROVOD_WITH_TENSORFLOW`) at compile time; listing it in
`environment.yml` would silently produce a CPU-only build. `install_horovod.sh` documents each step
and ends with `horovodrun --check-build` so you can confirm TensorFlow and NCCL are both enabled. The
NCCL path in that script is cluster-specific and may need adjusting.

TensorFlow is pinned to `2.15.0.post1` to stay on Keras 2 (`tf.keras`); version 2.16+ defaults to
Keras 3, which is incompatible with the model code.

The jet-clustering track additionally requires CVMFS (`run_centauro.sh` sources the LCG_109
`x86_64-el9-gcc15-opt` view for FastJet and the Centauro plugin).

## Running the pipeline

All Python entry points expect to be launched **from inside `scripts/`** — config paths are resolved
relative to `../configs`.

### 1. Event generation and data preparation

`pythia_generation/pythia_H1.cc` generates DIS events (Q² > 150 GeV², 0.2 < y < 0.7) at a chosen set
of generation parameters — currently α<sub>s</sub>, applied identically to the hard process, ISR and
FSR. It is compiled externally against Pythia8/ROOT/LHAPDF, following Pythia's `main341.cc` example.

The wrapper script runs generation, converts ROOT to HDF5, and derives network input features:

```bash
cd scripts
./generate_and_preprocess_pythia.sh <alpha_s> <n_events> <lepton_id>   # e.g. 0.118 5000000 -11
```

`lepton_id` is `-11` for positrons or `11` for electrons. To sweep α<sub>s</sub> from 0.10 to 0.20 at
1M events per point:

```bash
./run_all_alphaS.sh
```

This produces `*_prep.h5` files containing per-particle features (`Δη`, `Δφ`, `log pT`, `log pT/Q`,
`log E/Q`, `log E`, `ΔR`) and per-event features (`log Q²`, `y`, `e_pT/Q`, `e_η`, `e_φ`, weight).

### 2. Register samples in the manifest

Add each new file to `configs/dataset_manifest.yaml` with its parameter values:

```yaml
- path: pythia_H1_alphaS0.1180_eplus_5Mevents_prep.h5
  parameters:
    alpha_s: 0.118
  is_reference: true          # exactly one entry is the reference
- path: pythia_H1_alphaS0.1500_eplus_1Mevents_prep.h5
  parameters:
    alpha_s: 0.15
```

Paths are filenames only; they are joined at runtime with `--data_folder`, so the manifest stays
portable across machines.

### 3. Training

Choose which parameter points to train on by editing `data_files` in `scripts/train.py`, then:

```bash
cd scripts
srun --mpi=pmi2 python train.py --training_config config_surrogate.json
```

Use `srun`, not `horovodrun`, for multi-GPU runs on SLURM. Useful flags: `--data_folder`, `--nmax`
(cap events per sample, handy for quick tests), `--weights_directory`, `--verbose`.

The reference sample is selected automatically from the manifest's `is_reference` entry and
replicated once per data file, each copy labelled with that file's parameter values. This step is
essential: if the reference only ever carried its own α<sub>s</sub>, that input column would
perfectly identify the class and the classifier would ignore the physics entirely. The dataloader
splits the reference into disjoint chunks so no event is used twice.

### 4. Analysis

```bash
cd scripts
python analyze_classifier.py \
    --data_folder ../pythia_h5 \
    --weights_directory ../weights \
    --training_config config_surrogate.json \
    --data_file pythia_H1_alphaS0.1500_eplus_1Mevents_prep.h5 \
    --output_dir ./plots
```

Produces the training loss curve and, for every event- and particle-level feature, a three-panel
comparison of the unweighted reference, the model-reweighted reference, and the target sample, with a
ratio panel. `--data_file` selects which parameter point to reweight toward. Reweighting uses the
model's EMA weights.

`QA_plots.py` provides pre-training comparisons of raw feature distributions across samples, though
it currently needs updating to match the present dataloader API.

### Jet clustering (separate track)

`pythia_generation/cluster_jets.py` clusters final-state particles with FastJet (kT, R = 1.0) in the
lab and optionally Breit frames, computing substructure observables. This is an independent
substructure-analysis path; the ML classifier does not consume its output.

```bash
python pythia_generation/cluster_jets.py --input <in.root> --output <out.root> \
    --use_breit --use_centauro --lepton_beam -11
```

## Configuration

`configs/config_surrogate.json` holds training hyperparameters and the list of parameters fed to the
network:

```yaml
{
    'LR': 3e-5,
    'NEVT': 5,                    # physics event features (parameters are added on top)
    'NFEAT': 7,                   # particle features
    'PARAMETERS': ['alpha_s'],    # parameters used as network inputs
    'BATCH_SIZE': 128,
    'EPOCHS': 50,
    'MODEL_NAME': '...',
}
```

Despite the `.json` extension, this file is parsed as YAML — editors may flag it as invalid JSON,
which is expected. To add a second parameter, add it to each relevant manifest entry and to
`PARAMETERS`; `NEVT` and `NFEAT` stay unchanged.
